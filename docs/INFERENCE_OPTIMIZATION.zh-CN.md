# Qwen 推理优化报告

## 一、对比口径

本次优化使用冻结的 MAC V3 首轮答题阶段作为历史基线：

- 3,108 道题，对应 3,108 个不同视频；
- 使用 1 张 NVIDIA GPU；
- Qwen3.5-9B BF16，通过常驻 vLLM 服务推理；
- 客户端并发数为 8，服务端最大并发序列数为 8；
- 共完成 3,131 次 HTTP 请求，其中包含格式修复请求；
- 总耗时 6,468.47 秒，吞吐为 0.4805 题/秒；
- 历史官方得分为 0.8086。

`0.8086` 是冻结历史提交文件获得的官方成绩。服务器中没有 3,108 道题的隐藏标准答案，也没有官方评测器，因此无法在本地重新计算该分数。

为控制优化后的质量风险，实验保持原始 Prompt、生成参数和输出规则不变，并使用以下代理指标比较优化前后的结果：

- 输出格式通过率；
- 格式修复率；
- 答案点数一致率；
- 归一化答案一致率；
- 相对冻结 V3 答案的 Token-F1。

## 二、基准测试工具

`scripts/mac3108_benchmark.py` 读取原始视频以及冻结的 ASR、视觉和音乐证据，不修改原 AdVista 或 MAC-Agent 项目。

工具记录以下指标：

- 总墙钟时间和任务吞吐；
- 单题耗时、客户端排队耗时和服务端推理耗时；
- Prompt Token 和输出 Token 数量；
- HTTP 传输尝试次数和模型格式修复次数；
- 输出格式通过率；
- 相对冻结 `0.8086` 答案文件的质量代理指标。

每道已完成题目都会原子写入检查点。全量运行如果中断，可以使用相同实验名称和 `--resume` 继续：

```bash
.venv/bin/python scripts/mac3108_benchmark.py \
  --experiment full3108_bf16_c16_graph_prefix1 \
  --full --concurrency 16
```

## 三、最终服务配置

最终保留的 BF16 配置如下：

- vLLM 0.19.1；
- 1 张 NVIDIA H20；
- Qwen3.5-9B BF16 权重；
- 最大模型上下文长度 32,768；
- 最大并发序列数 16；
- 启用 CUDA Graph；
- 启用 Continuous Batching 和异步调度；
- 启用 Chunked Prefill，单批最大 8,192 Token；
- 启用 Prefix Cache；
- 视频仍采样 32 帧，与历史基线一致；
- GPU 显存利用率配置为 0.90。

正式服务启停命令：

```bash
bash scripts/start_qwen_service.sh
bash scripts/stop_qwen_service.sh
```

底层实验服务也可以通过参数启动：

```bash
QWEN_EXPERIMENT=bf16_c16_graph_prefix1 \
QWEN_MAX_NUM_SEQS=16 \
QWEN_ENABLE_PREFIX_CACHING=1 \
bash scripts/start_qwen_benchmark_server.sh
```

|---|---:|---:|---:|---|

| BF16，8 序列，Graph，Prefix | 0.4844 | 100% | 0.7311 | 保留 Prefix Cache |
| BF16，12 序列，Graph，Prefix | 0.5062 | 100% | 0.7249 | 可用 |
| BF16，16 序列，Graph，Prefix | 0.5182 | 100% | 0.7348 | 最终候选 |
| BF16，20 序列，Graph，Prefix | 0.5197 | 100% | 0.7367 | 仅快 0.29%，单请求延迟更差，淘汰 |
| BF16，12 序列，Eager，Prefix | 0.4717 | 100% | 首轮未记录 | 淘汰 |

16 序列 BF16 配置在保持 32 帧输入和质量代理基本稳定的情况下，相对当前环境 BF16 基线将样本吞吐提高了 10.64%。

由于 3,108 个视频均不相同，Prefix Cache 的实际命中率只有约 5% 至 6%，因此该项优化收益有限，符合预期。

## 五、为什么不采用 FP8 和减帧

### FP8

FP8 样本吞吐达到 0.6878 题/秒，速度提升明显，但 Token-F1 从 BF16 的约 0.7311 降到 0.5608，点数一致率也下降。因此不能仅为了速度采用 FP8。

### 视频从 32 帧降到 24 帧

24 帧配置吞吐达到 0.5404 题/秒，但 Token-F1 降到 0.6551，说明减少帧数会遗漏影响答案的视觉信息。因此最终配置仍保留 32 帧。

### 并发数提高到 20

20 序列相对 16 序列只提升约 0.29%，但单请求服务端 P95 延迟明显变差。综合吞吐和延迟后，16 序列更合理。

## 七、视频缺帧限制

16 路直接视频并发期间出现了 5 次视频加载警告。这些请求虽然成功返回，但实际读取的帧数少于预期的 32 帧，分别出现过只读取 22、1、14、8 和 23 帧的情况。

对低 Token 候选条目进行了低并发复测，所有复测均成功。但 vLLM 的 API `usage` 数据不包含实际视频帧数，服务日志也没有请求 ID，因此无法把每条缺帧警告可靠映射到具体题目。

该问题影响的是旧版“Qwen 直接并发读取视频”的基准任务。新 AdVista Agent 的 Stage 6 只读取文本 Evidence Ledger，不让 Qwen 并发解码原视频，因此新 Agent 的营销洞察流程不受该问题影响。

## 八、新 Agent 常驻服务接入

Stage 6 现在支持两种显式运行模式：

- `openai`：使用常驻的 OpenAI-compatible vLLM 服务；
- `subprocess`：保留原来的隔离冷启动 Worker。

默认配置使用 `openai`。如果服务不可用，系统会明确报错，不会静默启动第二份模型进程。

以下信息已加入 Stage 6 缓存身份：

- 运行模式；
- 服务地址；
- Served Model 名称。

`doctor` 现在也会检查：

- vLLM Endpoint 是否可访问；
- `AdInsight-RL` 是否在服务模型列表中，且服务端 `root` 是否与配置的 RL 权重目录一致。

## 十一、结论

本次优化得到两类收益：

1. 对原 3,108 题直接视频推理任务，在不采用 FP8、不减少视频帧数的情况下，将总耗时从 107.81 分钟降低到 98.39 分钟，吞吐提高 9.57%。
2. 对新 AdVista Agent 的文本 Ledger 洞察任务，通过常驻 vLLM 服务将 Stage 6 推理从 100.18 秒降低到 15.43 秒，提升约 6.49 倍。

最终保留的是质量风险较低的 BF16、16 序列、CUDA Graph、Chunked Prefill 和 Prefix Cache 配置。FP8 和视频减帧虽然更快，但因质量代理明显下降而未采用。
